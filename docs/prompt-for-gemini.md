# 给 Gemini 的写作包（任务与约束）

> 这是**第二份**文件。第一份是 `docs/fairy-persona.md`（角色卡：她是谁、怎么说话）。
>
> 若本机有 `../gemini-kit/02-fairy-samples.md`（原文台词范文，第三方文本，放在仓库外），
> 把它作为**第二份半**一起给，语感最准。
>
> 两份一起给：先给角色卡，再给这份任务与约束。两份合起来约 4 KB，一次就能带完。
> **不要**把游戏剧情原文/角色台词喂给它——角色卡里的规律已经够用，也不碰第三方文本。

## 一、怎么给（话术）

```
我发你两份材料：
1) Fairy 的角色卡（人物设定与说话方式）
2) 这次的写作任务与硬约束
请先读完再写，只输出「四、输出格式」规定的 JSON，不要解释。
```

然后依次粘贴 `fairy-persona.md` 与本文第 2 节起的内容。

若您只想发一份，就把 `fairy-persona.md` 第 9 节「一页精简版」贴在本文第 2 节前面——
精简版已经压掉了冗余，够 Gemini 抓住人设。

## 二、本次任务（先粘这段）

```
写 21 条中文短台词，用于「应用启动时的开屏问候」与「回合提示音」。共分 7 组：

A. 开屏问候，6 个时段，每段 3 条（共 18 条）：
   dawn       00:00–04:59   深夜
   morning    05:00–10:59   早上
   noon       11:00–13:59   中午
   afternoon  14:00–17:59   下午
   evening    18:00–21:59   晚上
   night      22:00–23:59   深夜
   同一时段的 3 条要有明显差异：一条「最稳的默认开场」（纯状态陈述），
   一条带数字癖或喜剧感，一条是请示或建议。

B. 提示音，3 条：
   thinking   回合开始（正在思考）  2–10 字
   done       回合正常结束          2–10 字
   failed     回合异常结束          2–10 字
```

## 三、硬约束（粘贴，这条最重要）

```
1. 开屏问候每条 12–28 个汉字（标点不计）。低于 12 字显得敷衍，超过 28 字会把开屏拖长。
2. 每条至多出现 1 个阿拉伯数字，且必须带小数（如 0.4 秒、87.1%）。
3. 每条至多使用 1 个协议标签（提示／警告／推测／检测到／查询完成／分析显示／提议／收到／
   很抱歉／肯定／否定）。不要两条都带标签。
4. 绝对不能断言会过期的信息：语音是固定文件，天天播放。
   禁止「今天有三项日程」「本周进度 60%」「还有两个待办」这类会变成假话的内容。
   只允许陈述恒定成立的系统状态（自检完成／就绪／待命／监控中／已记录在案）。
5. 不用 emoji，不用括号动作描写（如「（微笑）」），不用省略号「…」，不用 markdown 符号。
6. 不用生僻字与多音字（避免 TTS 读错），不用英文单词。
7. 同一时段的 3 条不得重复句式；不同时段之间也不要出现完全相同的句子。
8. 只输出 JSON，不要任何解释、不要 markdown 代码块以外的文字。
```

## 四、输出格式（粘贴）

```
严格输出如下 JSON（不要加注释）：
{
  "greeting": [
    { "file": "greeting/dawn-1.m4a",    "text": "…", "note": "一句话说明这条的结构" },
    { "file": "greeting/dawn-2.m4a",    "text": "…", "note": "…" },
    { "file": "greeting/dawn-3.m4a",    "text": "…", "note": "…" },
    { "file": "greeting/morning-1.m4a", "text": "…", "note": "…" },
    …（每个时段 3 条，共 18 条，顺序为 dawn→morning→noon→afternoon→evening→night）…
  ],
  "cue": [
    { "file": "cue/thinking.m4a", "text": "…", "note": "…" },
    { "file": "cue/done.m4a",     "text": "…", "note": "…" },
    { "file": "cue/failed.m4a",   "text": "…", "note": "…" }
  ]
}
```

## 五、自检清单（也粘给 Gemini，让它自查后再回答）

```
回答前逐条自查，任何一条不满足就重写那一句：
[ ] 每条都是 12–28 字（提示音 2–10 字）？
[ ] 每条最多一个数字，且带小数？
[ ] 每条最多一个协议标签？
[ ] 没有任何会过期的信息（日程、进度、待办数量、具体日期时间）？
[ ] 没有 emoji、括号动作、省略号、markdown 符号、英文单词？
[ ] 6 个时段共 18 条，没有重复句子、没有重复句式？
[ ] 每条听起来都像"开机时说的那句"，而不是"对话中的回复"？
```

## 六、反例（给 Gemini 看，避免它写成这样）

| 不要这样写 | 原因 |
|---|---|
| 主人，今天有三项日程，需要我为您安排吗？ | 静态音频，明天就变成假话 |
| 提示，检测到网络波动，建议稍后重试。 | 两个标签 |
| 主人～下午好呀！一起加油吧 (๑•̀ㅂ•́)و✧ | 卖萌 + emoji，违反人设 |
| 分析显示，本机已就绪，随时待命。 | 「本机」是禁用的自称 |
| 主人，我已巡查 3 轮，共检查 12 个模块，耗时 1.4 分钟。 | 数字过多，读起来像念经 |
| 主人，我在这儿。 | 太短（少于 12 字），且过于随意 |
| 很高兴为你服务，希望你喜欢！ | 人设不是客服腔 |

## 七、参数建议与交付后处理

- 温度 1.0–1.2（需要一点幽默感）；若多次输出雷同，把「同一时段三条要有差异」再强调一遍。
- 一次给全 21 条；不要让它分批写，否则跨批次的句式会重复。
- 拿到 JSON 后存成 `docs/voice-lines.json`，本地跑：

  ```sh
  node tools/check-lines.mjs docs/voice-lines.json    # 字数/标签/数字/禁用字符/重复句/每档条数
  node tools/render-lines.mjs                         # 从 JSON 重新生成台词表
  ```

- 校验不通过就把它报的错原样贴回 Gemini，让它**只改那几条**，别让它整批重写。
