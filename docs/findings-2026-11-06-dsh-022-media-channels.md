# DSH 0.2.2 之后：哪些通道还稳，以及"提示音吞开头"的完整结论

日期：2026-11-06
环境：DSH 桌面版 **0.2.2-rc.1**（此前 0.2.1-rc.3），Electron **44.7.0**（未变），Windows x64。

## 一、版本事实

| 项 | 0.2.1-rc.3 | 0.2.2-rc.1 |
|---|---|---|
| Electron / Chromium | 44.7.0（Chromium 152） | **44.7.0（未变）** |
| 本机 HTTP 监听端口 | 有（插件路由直连 localhost） | **无**（App 不占任何 TCP 端口） |
| 新增依赖 | — | `@deepseek-ai/dsh-api-gateway`（`main.js` 引入 `REMOTE_STREAM_MUX_PATH`） |

结论：**不是浏览器内核升级**，而是壳子把插件路由/流改经网关中继。

## 二、通道实测（客户端里发请求，结果写进窗口标题读出）

| 通道 | 实测 | 说明 |
|---|---|---|
| `GET /hdd/report` | `200` | 返回日志尾部，稳定 |
| `GET /hdd/report?event=…` | `204` | 写日志，稳定（写完日志里能查到） |
| `POST /hdd/report`（JSON 正文） | `204` + 日志有对应行 | **也稳定**——先前判它"失效"是错的 |
| `GET /hdd/asset?path=cue/thinking.m4a` | `200` / 5484 字节 | 与文件实际大小一致，字节完整 |
| Cordis 槽位 / 主题令牌 / 宿主事件 | 正常 | 徽记、设置页、状态条、cue 决策都工作 |

## 三、真正的元凶：`MAX_LOG_BYTES` 从未定义

`lib/index.js` 里有一段判断 `if (existing.length > MAX_LOG_BYTES)`，而 **`MAX_LOG_BYTES` 只被引用、从未声明**。
于是 `/hdd/report` 的每一次写入都在这一行抛 `ReferenceError`，又被路由自己的 `catch {}` 吞掉：

```
客户端 POST → 路由 handler → appendLine() → ReferenceError → catch{} → 返回 204
                                                                  ↓
                                                        日志里什么都没有
```

**症状**：日志只有宿主自己写的行（`host-apply`、`cue`、`cue-deliver`），客户端的
`apply` / `assets` / `splash-*` / `cue-play` 一条都没有。
**代价**：整整两天的排查都是在"看不见客户端"的情况下盲改（还因此错判成"POST 正文被网关吞掉"）。
**修法**：补上 `const MAX_LOG_BYTES = 2 * 1024 * 1024`。

## 四、提示音吞开头的完整结论

| 阶段 | 写法 | 结果 |
|---|---|---|
| 最初 | `new Audio(url).play()` | 0.2.2 起开头几十毫秒被吞（媒体元素"够到数据就出声"） |
| 第二版 | fetch → `decodeAudioData` → 缓冲排期 | 大部分时候好了，**静置后的第一声仍缺** |
| 终版 | 上面 + **静音保持**（-80dB 振荡器）+ 排期提前量 **0.6s** + 上下文跨重载复用 | 稳定，多次验证无吞音 |

素材不是问题：`cue/thinking.m4a`（"推演中。"）0–30ms 就有信号，**零前导静音**——所以任何起播
延迟都会立刻被听成"吞了前半个字"，这也是这个问题特别刺耳的原因。

## 五、教训（比结论更值钱）

1. **"日志里没有"不等于"没发生"**。先验证日志通道本身，再谈现象。
2. **诊断代码不要 `catch {}` 吞掉一切**：写日志失败一次就该在别处留痕，而不是静默 204。
   现在 `/hdd/report` 的失败分支已经不会把"写失败"伪装成"写成功"。
3. **播放正确 ≠ 出声正确**：`ctx=running`、`lead=0.6`、`setup=7ms` 都齐了，设备仍可能需要时间唤醒。
4. **别用猜测代替读数**：窗口标题是唯一能穿透渲染层到外面的通道，但它是临时手段，
   上报通道修好后应立刻回到日志。
5. 报告的判断（"POST 被网关吞掉"）在没有可观测证据前不要下定论——本次就是反例。
